# Acquisition-only feedback experiment: unsuccessful UX result

> Historical investigation record. See the [current resize investigation](../README.md) for current decisions and next steps.

User observation: **后者卡顿似乎更严重一点点**. Do not promote acquisition-only
feedback collection as a fix. The diagnostic remains default off.

- Control: `logs/live-resize-20260911-084833-fa92b2b4`, runtime activation false.
- Treatment: `logs/live-resize-20260911-084930-b8b46bc6`, runtime activation true.

Percentiles use nearest rank over completed resize frames (or their stage events).
Different hand-driven workloads, truncated tails and substantial instrumentation
overhead prevent a causal regression claim from this one pair. The measured tails
are consistent with the user's report; they do not establish why the treatment felt
worse. Fewer instrumented drains also reduce tracing work, so the reduced drain total
cannot be attributed entirely to less driver/API work.

The intended call-site change is confirmed: treatment drains occur under viewport
acquisition, while control drains also occur in platform update/render collection.
Statistics item counts per frame have median 2 in both prefixes. The maximum is 4 in
control and 11 in treatment; counts alone do not establish sustained queue growth.

Treatment frame 1354 totals 30.7205 ms. Its resize is 14.5538 ms, including
13.9086 ms buffer reset and 11.8884 ms slot-1 texture Release. Present is 8.8378 ms;
the statistics drain is 1.3630 ms. Nested values must not be summed together.
Frame 741 also has a 9.4884 ms release of slot-2 `presentation_buffer`; expensive
release is therefore not restricted to the texture interface in this capture.
Other frames can have delays elsewhere; these examples do not explain every slow frame.

## Decision

Stop pursuing reduced feedback drain frequency as the proposed stutter fix on the
strength of this experiment. Retain its code as an explicitly disabled diagnostic,
with the ordinary default unchanged. Do not repeat this same manual A/B now.

The next resource strategy proposal should address the synchronous replacement of
all three buffers per size change, with explicit allocation-generation identity,
memory bounds, availability/ownership rules and fallback behavior. Moving Release
to another call site or thread without those rules is not an established solution.
This pair alone does not authorize implementing that separate resize policy.

Before any further interactive evidence request, fix capture-window control so
setup and idle work cannot consume the whole file budget. Repeating instructions
to drag for fewer seconds has proved insufficient. Do not raise the bound merely
to conceal incomplete evidence.
