## Main window: deferred updates during native modal size/move

All 11 observed native size-move intervals contain zero RenderFrame, zero renderer
resize, and zero Present events. They include moves as well as possible resizes;
their count is not a count of distinct size-changing drags.

The longest interval runs from 10.616969 s to 25.196998 s (14,580.029 ms).
The enclosing outer message batch takes 14,580.684 ms; invalidation-to-frame latency
reaches 14,580.583 ms. At 25.198312 s the main resize completes in 0.8383 ms,
changing the requested buffer size from 2240×1435 to 1857×1483. Completion is
approximately 1.314 ms after the modal exit event.

The source explains the observed sequencing: the outer loop dispatches messages
before calling RenderFrame; WM_SIZE only replaces `pending_resize_`; RenderFrame
later calls ApplyPendingResize. The trace is consistent with dispatch remaining
inside the native modal loop until exit. Main resizing therefore supplies no
continuous-rendering control case for detached live resizing. This behavior is
separate from the detached performance issue and changing it would be a policy change.

53.250709–56.098394 s (245) and 62.603640–70.309311 s (723). It has no native

must not be added as if they described the same operation.

intervals, not physical display/scanout intervals.

There are three detached acquire retries in the complete recording, with
DXGI_ERROR_WAS_STILL_DRAWING, and no failed resize or Present calls. Two retries
occur just after the long resize cluster, the third during the later short-lived
detachment. The approximately 101.832 ms main available-wait outlier occurs at
85.721325 s, outside the measured long-lived detached resize interval; it must

## Largest stalls remain outside the measured resize calls

Frame 2862 ends at 68.786556 s and takes 113.2705 ms. Its render_pass is
110.2175 ms, but detached resize takes only 1.2250 ms, detached Present 1.5093 ms,
main Present 0.1324 ms, and both available waits approximately 0.001–0.002 ms.

The event-to-event gap from main viewport_acquire end to detached viewport_resize
begin is 106.8833 ms. Frame 2968 has an analogous 89.1302 ms gap; frame 3008 has
64.2475 ms. This region includes main ImGui draw submission, optional capture
handling, and the beginning of ImGui::UpdatePlatformWindows before the renderer
resize callback. Capture is disabled in the recording's runtime configuration.
The current trace does not distinguish main draw submission from platform-window
updates or time spent descheduled within them. It does not prove a particular
Win32 call, driver operation or allocation strategy causes these stalls.

Next diagnostic scope: separate main `ImGui_ImplDX11_RenderDrawData` and
`ImGui::UpdatePlatformWindows`, then narrow the latter's platform position/size
callbacks if indicated. Retain current resize/presentation policy. Buffer reset
is a measured cost worth investigating, but optimizing it alone is not established
as the fix for the largest observed stalls.

## Instrumentation limitation exposed by this run

The final main lifetime-end event is incorrectly labeled `viewport_role=detached`
after the native main HWND has already been cleared. HWND 6030638 and lifetime 1
remain intact and match its main lifecycle begin; all main runtime resize/Present
events precede this teardown and the analysis uses that lifetime identity.
The current checker accepts this role mismatch. A follow-up telemetry correction
should retain role across teardown and test role consistency per lifetime; the
original recording must remain unchanged.

Follow-up instrumentation now times main/detached draw submission, platform
update/render, and position/size callbacks separately. Main role is retained at
registration, and new machine checks reject lifetime-role changes. The original
capture's pass result above describes the checker at the time of analysis; the
tightened checker correctly rejects its known teardown role mismatch. No new
performance result is claimed until the detached-only repeat is collected.
