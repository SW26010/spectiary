# Detached resize: buffer lifetime and feedback call-site review

> Historical investigation record. See the [current resize investigation](../README.md) for current decisions and next steps.

Review date: 2026-09-11. This is a proposal, not an implemented policy change.
The failed B UX outcome remains in force. See
[08:20 evidence](../evidence/20260911-082026-feedback-release.md).

## What the current code does

`SetViewportWindowSize` calls `D3D11WindowPresentation::Resize`, then
`CollectPresentationUpdate`. The Composition resize unbinds render targets and
calls `CreateBuffers`. That synchronously resets all three slots, changes the
source rectangle, and creates three exact-size displayable textures, render-target
views, presentation buffers and available-event handles. Each slot releases its
event handle, presentation buffer, render-target view, then texture. No retired
generation list or resize-time availability check exists. The next BeginFrame
waits on the *new* slots; it cannot explain a preceding old-texture release wait.

The surface's new buffer binding is set in Present, after drawing. Application
COM reference release does not establish when every system-held reference ends.
The trace does not expose the exact previously bound slot or allocation generation.
Consequently the observed fence wait in Present cannot yet be assigned to a
specific old allocation, even though its kernel call path is resolved.

Feedback collection is coupled to transition collection. `CollectPresentationUpdate`
always calls `TakeCompositionFeedback`, whose `TakeFeedback` first drains statistics.
The 120-submission threshold only gates emission of the accumulated report; it does
not gate draining. Statistics update reporting counters in this implementation;
they do not select buffer slots or drive the available-event wait.

For a successful detached resize frame without a monitor change:

| Point | Statistics drain |
| --- | --- |
| After resize, in UpdatePlatformWindows | TakeFeedback |
| Before buffer acquisition | BeginFrame |
| After drawing, before Present | TakeFeedback |
| After Present | TakeFeedback |

Creation, monitor refresh and skipped acquisition add other collection paths.
Main-window feedback is collected separately by `LogPresentationUpdates`.
This review does not assume it has identical call frequency.

## Concrete next experiment proposal

First isolate **feedback drain frequency**, because it is a smaller change than
buffer lifetime management. Do not combine it with a new buffer strategy or
promote the no-redirection flag to production.

Proposed experimental behavior: separate draining from taking accumulated feedback
and transition reports. For the experimental detached path, drain once at a defined
per-viewport frame boundary (before acquisition), while existing collection sites
continue to report transitions and accumulated counters. Keep the current loop,
statistics kinds, error reporting, zero-timeout checks and available-buffer policy.
Treat this as an explicit diagnostic behavior change, default off. Preserve the
ordinary baseline and compare only one changed factor at a time. If B is held fixed
for this diagnostic, any result applies to B until reproduced on the ordinary path.

Machine-checkable requirements before an interactive trial:

- Exactly one drain attempt per participating viewport/frame in the experimental
  path, including acquisition failure/skip; distinct viewports retain distinct state.
- Taking transitions or accumulated reports does not drain again. Counters remain
  cumulative across report thresholds, and a statistics error remains observable.
- Destroy/recreate and fallback reset experiment state; no cross-lifetime suppression.
- Resize dimensions, three-slot creation/release sequence, wait timeouts, native
  callback forwarding, Present mode and API-result handling stay unchanged.
- Compare GetNext item counts, queue-drain duration, total RenderFrame duration and
  user-perceived stutter. A faster resize callback with the same delay before drawing
  is not sufficient evidence of improvement. Reject incomplete/dropped profiles.

This experiment cannot remove the independently observed texture-release or Present
fence waits. Its likely scope is limited; it tests whether repeated collection sites
and their timing contribute, rather than promising a fix.

## Buffer strategy is a separate design decision

The stronger resource-lifetime candidate is incremental replacement of buffers,
instead of synchronously replacing all three for every size. Microsoft provides
an example of spreading replacements across presents; that is API support for an
approach, not evidence that it fixes this application. See
[Composition swapchain examples, example 15](https://learn.microsoft.com/en-us/windows/win32/comp_swapchain/comp-swapchain-examples#example-15staggered-buffer-resize-operation-for-improved-performance).

Before implementing that policy, specify exact-size selection during continuously
changing dimensions, available-buffer ownership, a strict memory/generation bound,
partial-allocation failure and DXGI fallback, teardown, and source-rectangle validity.
Moving Release to a worker alone is not a justified substitute: it can merely move
the wait and introduces ownership/teardown coordination.

The API describes GetNext as reading a queued statistics item, without a latency
bound. A signaled statistics event therefore is not evidence that GetNext will
return without internal contention. See
[GetNextPresentStatistics](https://learn.microsoft.com/en-us/windows/win32/api/presentation/nf-presentation-ipresentationmanager-getnextpresentstatistics).

No product source, scheduling policy, resize strategy or presentation strategy is
changed by this review. No additional interactive capture is needed to establish
the call graph and counts above.
